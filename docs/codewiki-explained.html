CodeWiki 使用说明

把代码变成团队可用、可验证、会持续变好的业务知识

CodeWiki 不试图替代开发者读代码；它先把最常被问、最难一次讲清的业务主脉络沉淀下来，让人和 AI 都从同一份可靠起点开始。

为什么存在拿到后怎么用怎么生成知识怎么分层如何检索如何评估如何变好

一、CodeWiki 解决什么问题？

生产项目的困难不在于“代码找不到”，而在于人提出的是业务问题，代码保存的是实现细节。

语义差距

用户问“什么时候能退款”，代码里往往是状态、接口字段和分支条件，没有“退款规则”这四个字。

链路太长

一个功能可能跨页面、状态管理、接口、消息队列和后端服务。让 Agent 每次从头读，很容易漏环节。

答案不稳定

不同模型、不同上下文、不同提问方式，都可能让一次性代码分析得到不同结论。

经验无法复用

开发者已经摸清的主链路、缺陷、边界和决策，如果不沉淀，新人、产品、测试和下一位 Agent 都要重来。

CodeWiki 的选择：不建设一套重型在线 RAG，也不让 Agent 每次从零读仓库；而是把代码“编译”为带证据的业务文档和结构化索引，一次生成，反复检索，通过 Git 共享。

二、用户拿到之后怎么用？

安装只需要一次：npx codewiki init。之后大多数操作都在 Claude Code 或 Codex 中用自然语言完成，不必记内部命令。

1. 首次为一个业务模块建立知识

为订单模块生成知识库：前端在 apps/order-web，Java 服务在 services/order-api。

CodeWiki 会理解这是一个跨前后端模块，生成业务视角、研发视角、代码导航与回归 Case。

2. 日常提问

什么情况下允许退款？请基于 CodeWiki 和代码证据回答。

回答会先从已有知识中找主脉络；需要技术细节时，再附上相关文件、字段或调用路径。

3. 代码变化后更新

更新订单模块知识库，只处理这次代码变更影响到的知识。

不是重新写全量文档，而是先判断变化是否影响业务语义，只更新需要变化的内容。

4. 看质量、给反馈

检查订单模块的知识置信度，并告诉我哪些真实问题缺少 Case。
没帮助，答案没有说明“未发货”这个限制。

每次基于 CodeWiki 的回答末尾都会询问“这次检索有帮助吗？”。说“有帮助”会把这次真实问题自动沉淀为带检索证据的反馈 Case；说“没帮助”会留下可追踪的 Gap，待补齐知识后再关闭。

三、知识是怎样生成的？

生成不是“把仓库丢给 LLM 写总结”。它由确定性分析打底，再让 LLM 做适合它的工作：解释业务含义、组织成适合人阅读的问题与文档。

确定模块边界哪些目录、前端、服务属于同一条业务链路
→
AST 分析提取组件、函数、接口、状态、事件、字段和调用关系
→
统一代码图把多语言、多目录事实连成可导航的关系网
→
LLM 增补文档基于事实写出业务流程、规则、风险与影响面
→
证据校验与回归确认每条关键结论能回到代码，Case 不退化

AST 和 LLM 各自负责什么？

工作主要承担者原因
找到函数、组件、接口、事件、文件关系AST / 静态分析结果稳定，可重复，不依赖模型理解力。
识别调用链、字段流向、跨语言连接AST + 规则 + 图索引保留可追溯的代码事实。
解释“这条链路对用户意味着什么”LLM把实现细节翻译成业务语言，形成易读的主脉络。
核验关键结论证据绑定 + 回归 Case避免文档只是看起来合理，实际却与代码脱节。

从 AST 事实到知识前，还会做哪些整理？

AST 只会给出大量离散事实，例如“这个组件引用了那个 Store”“这个函数调用了那个接口”。CodeWiki 还需要把它们组织起来，才能形成适合生成和检索的主脉络。

整理能力原理解决的问题
社区聚合在文件/调用关系图上，按关系的可靠度给边加权；使用 Louvain 社区发现把连接紧密的节点聚成一组。算法不可用时退回到连通分量。从成千上万个节点中找出天然属于同一功能域的一团，例如“订单创建”“支付回调”或“对话面板”。它用于发现和归纳候选主链路，不替代用户确认的模块边界。
关键节点排序计算 PageRank、介数中心性和连接度。重要度高的节点，通常是被大量依赖、连接多个子链路或处于必经路径上的节点。让生成和检索优先关注入口、枢纽、核心 Store、接口契约等，而不是平均对待每个工具函数。
字段血缘从页面模板绑定出发，关联组件使用的 Store，再沿 Store 自身或其 import 找到接口候选；形成“页面字段 → 状态 → 接口”的链。已逐项验证的链路才能进入反向索引。回答“这个字段从哪里来”“改接口字段会影响哪些页面”。不确定的关系会带置信度，不会伪装成事实。
多字段检索索引将文档的标题、别名、常见问题、业务实体、章节和正文分别建立词项索引；同一词在不同字段的权重不同。用户说“退款条件”，即使代码里只有状态名或接口字段，也可以借助文档中的业务别名和问题找到正确主题。
要点：社区聚合、关键节点排序和字段血缘都是“整理代码事实”的确定性算法；LLM 只在这些事实已经准备好之后，负责把它们解释成业务文档。不是由 LLM 猜出一张图。
Product业务流程、规则、边界，面向产品和测试。
Developer架构、状态、影响面，面向研发。
Navigation机器可用的代码图与链路索引。
Quality缺陷、事故、决策和已确认反馈。

四、知识为什么要分层？

不是所有从代码里提取出来的信息都适合叫“Wiki”。真正要被团队阅读和提交到 Git 的，是能解释业务、帮助决策的知识；图索引、缓存、事务和个人反馈只是支撑它运转的内部数据。

层保存什么谁主要使用默认是否展示 / 提交
Product用户流程、业务规则、能力边界、验收口径。产品、测试、业务负责人、新成员。默认展示；提交 Git
Developer核心架构、调用主链路、关键状态、影响面，以及确实重要的异常边界。研发、排障与变更评估人员。按需展开；提交 Git
Quality已确认的缺陷、事故、决策和用户反馈修正；每条都应有证据与回归约束。研发、QA、负责人。按需检索；提交 Git
NavigationAST 生成的文件、函数、组件、接口、事件与跨语言关系图。检索工具和需要追源码的研发。默认隐藏；作为证据索引提交 Git
本地运行数据缓存、检索记录、用户评分、Gap 状态、评估运行记录、生成事务和失败现场。工具自身与质量诊断人员。不展示为 Wiki；不提交 Git

用户应该看到的层次

默认回答先给 Product 的业务结论：流程、规则、边界
→
需要解释时展开 Developer：实现主链路、状态和影响面
→
需要证明时附 Navigation 的少量代码证据，不抛出整张图
→
出现问题时才查看 Quality 与本地诊断数据

这条策略要解决什么？

  • 产品和测试不需要看到“图节点、截断、缓存、事务、回滚”等工具术语。
  • 研发不必每次从全量代码开始，但仍能在需要时追到准确的文件和行号。
  • 缺陷与决策是重要资产，但不能污染正常业务主叙事；只在相关问题被问到时参与检索。
  • 缓存、日志、个人反馈和失败现场帮助工具可靠运行，却不应该进入团队 Wiki 或 Git 历史。
原则：默认给人看“结论和主脉络”；按需给研发看“实现和证据”；仅在诊断时暴露“运行细节”。分层不是多写文件，而是控制不同信息何时出现、给谁出现。

`.codewiki/` 目录里每一类内容是什么？

下面这张表是给维护者看的。普通使用者只需要关心 modules/；其余目录不应出现在 Wiki 预览或日常回答中。

目录或文件用途是否属于团队知识是否提交 Git
modules/正式知识库：Product、Developer、Quality、Navigation 和检索 Case。是是
cache/生成和检索的临时缓存，用来避免重复解析同一批源码、提高速度。删掉后可重新生成，不影响正式知识。否否
transactions/生成事务的快照与失败现场。生成前保存旧版本；校验或 Case 失败时恢复旧知识，便于排查失败原因。否否
evaluation-runs/内部冒烟检查的详细结果，用于发现索引或证据链路退化。否，属于本地评估记录否
knowledge-health/健康报告的历史快照，供工具诊断和趋势分析。否，属于本地质量记录否
retrieval.jsonl每次真实检索命中了什么模块、知识和代码证据；用于统计模块命中和 Case 覆盖。否，可能含个人问题否
feedback.jsonl / gaps.jsonl用户“有帮助 / 没帮助”的反馈，以及尚未解决的知识缺口。否；好评自动沉淀为反馈 Case，差评经补充和确认后转化为知识与 Case否
workflow/给 Claude Code 和 Codex 的工作流说明、模板和参考资料，不是某个业务模块的知识。否由工具安装与升级管理
简单理解：modules/ 是“出版物”；cache/ 是“草稿纸”；transactions/ 是“撤销保险”；评估、检索和反馈文件是“使用数据”。它们各有价值，但不应该混进用户阅读的 Wiki。

五、提问时，CodeWiki 到底做了什么？

codewiki_explore 是一个 MCP 检索工具，不是 Skill，也不是“再让 Claude 读一遍代码”的提示词。

普通 Skill 让 Claude 直接读代码CodeWiki 的方式
Skill 的角色告诉 Claude 应该如何行动，例如“去读这些文件、总结答案”。仍然是工作流说明：遇到相关问题时，调用检索工具。
真正的检索Claude 临时决定搜什么、读多少、如何归纳。本地工具从已生成的文档、索引与代码图中按固定规则找结果。
上下文可能读取大量源码，占用上下文，并随模型变化。只返回少量相关知识摘要、链路和代码证据。
稳定性同一问题可能因模型或提示变化而走不同路径。检索路径、命中模块、证据和评分可记录、可回归。
一句话区分：Skill 是“操作说明书”，告诉 Agent 什么时候用什么能力；codewiki_explore 是真正执行检索的本地工具。Agent 负责把结果讲成人话，但不应由 Agent 临时决定全部检索事实。

检索过程

理解问题类型例如业务规则、调用链、字段来源、影响面、状态问题
→
召回业务知识优先匹配标题、别名、常见问题、实体与正文
→
扩展代码图按问题类型选择相关关系，限制深度和数量
→
返回小而准的上下文模块、知识、证据、调用路径、是否可能过期

“模糊搜索、多匹配”具体是什么意思？

它不是向量检索，也不是让模型猜相似度。当前的“模糊”来自可解释的词项匹配：

  • 英文、标识符和数字会规范化为可检索词项，例如 refundStatus、order-api。
  • 中文会拆成连续的双字词片段，因此“退款条件”“退款规则”会共享“退款”等片段，而不要求用户完全复述文档标题。
  • 同一个词命中标题的权重大于别名，别名大于常见问题、业务实体、章节，正文权重最低。
  • 一个问题可以同时命中多篇知识；检索器会按总分排序，默认只返回前几篇，而非拼接全部文档。

这带来的好处是结果稳定、可调试、无需 embedding 服务；代价是同义词覆盖依赖文档的别名和问题设计，需要通过真实反馈持续补充。

不同问题为什么会走不同检索路径？

问题类型例子检索策略
业务语义“什么情况下允许退款？”文档优先，再补少量直接证据。
调用链“提交订单后经过哪些服务？”从函数、事件、接口节点出发，沿调用和触发关系扩展。
影响分析“改这个接口字段会影响哪些页面？”从接口/字段节点反向和正向遍历调用、依赖、渲染关系。
字段血缘“订单金额从哪里来的？”优先沿“接口 → Store → 页面字段”的关系寻找来源和消费方。
状态与异常“处理中怎么会变成失败？”优先使用状态转换、异常条件和恢复关系，再结合解释文档。

图扩展不会无限进行：它只允许与当前问题类型相关的关系，跳过低置信关系，并限制层数、文件数和返回证据数量。这样既能拿到链路，又不会把整仓代码塞进 Agent 上下文。

检索结果怎样被使用？

codewiki_explore 返回的是结构化“资料包”：命中模块、知识摘要、代码证据、关联路径、是否可能过期，以及本次检索 ID。Claude Code 或 Codex 再根据这份资料包组织自然语言答案。检索结果会记录在本地，用户评分后可用于统计模块命中、发现缺少的 Case 和补充知识。

因此：“普通 Skill 让 Claude 搜代码”是由 Agent 临时决定资料；“CodeWiki Skill 调用 Explore”是 Skill 负责调度，Explore 用固定索引和固定规则准备资料，Agent 只负责解释。这就是两者最核心的区别。

六、怎么评估它有没有价值？

不能只看“回答看起来不错”，也不能只看一组自动生成题是否通过。CodeWiki 的用户报告只展示最能反映真实使用的四件事。

1. 知识是否需要更新

知识生成时的 Git 提交与当前代码相差多少提交；有变更时提示更新。

2. 真实问题有多少

统计最近一段时间用户实际问过的去重问题，而不是工具预设的题目。

3. 有多少问题已验证

用户确认“有帮助”的问题会成为反馈 Case；尚未沉淀的问题就是下一批待补资产。

4. 有多少未解决 Gap

“没帮助”或明确未命中的问题会形成 Gap，直到知识补齐并验证。

Case 是什么？

Case 不是一条 FAQ。它是一份可重复验证的真实问题：给定一个问题，应该找到哪些知识和代码证据；或明确规定这个问题不应该有答案。

问题：什么情况下允许退款？ 期望：命中“退款规则”知识，并给出对应状态判断的代码证据。

用户给出“有帮助”后，系统会把该问题、检索记录和当时的知识证据写成 feedback 来源的 Case；之后相同问题可持续验证。来自测试、缺陷单、PRD 或人工整理的问题也可以成为 Case。自动生成的基础题只用于内部确认检索链路没有坏掉，不计入用户看到的 Case 数量或质量结论。

用户看到的健康报告

| 关注项 | 当前状态 | 说明 | | --- | --- | --- | | 知识状态 | 当前 / 需更新 | Git 落后多少提交、是否有未提交改动 | | 历史检索问题 | 7 个 | 去重后的真实用户问题 | | Case | 2 个已验证 | 已验证、待补、待复核的数量 | | Gap | 0 个待处理 | 当前尚未解决的知识缺口 |
不会出现在用户报告里的内容：自动题回归通过数、评分等级、命中率、检索耗时、模型内部候选分数、证据条目数量和历史对比。这些是工具诊断数据，不是用户判断知识是否有用所需的信息。

七、它如何持续变好？

CodeWiki 的改进不是让模型“下次聪明一点”，而是把真实问题转成团队可共享、可回归的资产。

用户提问
检索并回答
用户反馈
沉淀 Case 或 Gap
补知识并验证
  1. 用户提问后，系统记录命中模块、知识、证据和检索 ID。
  2. 用户说“有帮助”，系统立即将本次问题沉淀为带检索证据的反馈 Case。
  3. 用户说“没帮助”，系统建立一个 Gap：问题在哪、哪次回答、属于哪个模块。
  4. 开发者或 Agent 回到源码、测试、提交等证据确认事实，再补充正确知识和对应 Case。
  5. 新知识验证通过，Gap 才关闭；以后再退化，Gap 会重新打开。

缺陷、事故和重要决策也走同一个入口，只是会写入 quality 层。这样它们不是散落在聊天记录或 issue 中，而是与代码知识一起参与检索和验证。

最终效果：一个人补过的知识，不只解决一次回答；它会通过 Git 成为团队资产，并在后续更新中持续被检验。

从哪里开始？

建议先选一个边界清楚、团队经常讨论的模块。先生成，再让研发、产品、测试各自拿 5～10 个真实问题试用并评分。不要急于追求文档数量；优先让主链路、关键规则、状态异常和无答案边界可靠起来。

CodeWiki 的目标不是取代源码，而是把“应该先知道什么、该去哪里验证”稳定地交给每一位团队成员和每一个 Agent。
