# /codewiki Output Schema Reference v3.6

> v3.6 变化（本文件末尾集中记录 §「v3.6 新增 Schema」）：
> - `field-lineage/{index,pages/*,reverse-index}.json` — 字段级溯源
> - `_intermediate/{field-candidates,pinia-stores,api-payload-shapes,flows}.json` — 中间产物契约
> - `graph-index.json` 新增 `structuralFingerprint` / `fieldFingerprint` / `page_fingerprints`
> - `.draft.json` / `.review.json` — 主对话流窄字段契约
> - `field_lineage_llm_patch` — LLM 补证子任务返回结构
> - `template-render-rules` — 产品层 §2 从 JSON 渲染 markdown 的算法
> - Markdown `kb:*` / Navigation `nav:*` 稳定 ID + `bindings.jsonl` 双向绑定
> - `.codewiki/cache/codewiki/` 派生检索索引（不提交）

This document defines the exact output format for all files generated by the /codewiki skill.

**v3.6 关键契约**：
- codewiki 重新定位为「面向角色与 AI 检索的模块知识库生成器」，同时服务 PM/QA/前端/AI 四类受众
- README 升级为「角色路由器」（不再只是文件索引）
- Product 层固定 3 大块；Frontend 层固定 3 文件 + 一行元数据头
- Navigation 层新增字段级溯源、反向索引、稳定 ID、`bindings.jsonl`；`navigation/index.yml` 降为无 MCP 后备入口
- Manifest 使用 `version: "3.6"`，覆盖断言扩展为 12 项
- 反捏造规则按事实类型分级；严禁输出工时/人天估算

文档结构模板的细节集中在 `references/role-templates.md`，本文件聚焦 schema 与产物清单。

---

## 设计原则

| 层 | 角色 | 核心目标 | 组织方式 |
|---|------|---------|---------|
| `README.md` | 总入口 | 角色路由：PM/QA/前端/AI 各看哪几篇 | 角色阅读路径 + 任务入口 + 可信状态 |
| Layer 1 `product/` | PM/QA/业务 | **写 PRD + 验收**——能力边界、用户感知、影响面 | 按业务流组织，3 大块固定模板 |
| Layer 2 `frontend/` | 前端 + AI | **建立实现心智模型**——主链路、状态、分支、异常恢复 | 按架构域组织，3 文件 + 一行元数据头 |
| Layer 3 `navigation/` | AI/工具 | **完整可追证的检索**——业务概念、字段、状态、事件、调用链 | AST 产出 + 行为索引 + 路由索引 |

**关联机制**：Product/Frontend Markdown 用 `kb:*` 稳定 ID 承载业务/技术语义，Navigation JSON 用 `nav:*` 稳定 ID 承载代码事实，`bindings.jsonl` 建立多对多关系。Claude Code 通过 `codewiki_explore` 执行“语义文档 → 代码图 → 关联文档”；README 与 `navigation/index.yml` 只做人类入口和无 MCP 后备。

## Layer 1: `docs/<module>/product/`

Product/Frontend Markdown 共用以下 frontmatter。`id` 一旦发布不可因标题或文件重命名而改变；正文保持自然语言，不复制 JSON 结构。

```yaml
---
id: kb:<module>:product:<topic>
kind: business                  # business | technical
title: "<用户会使用的业务标题>"
aliases: ["<按钮文案>", "<页面别名>", "<业务同义词>"]
questions:
  - "<用户可能如何提问>"
entities: ["<业务实体>", "<页面/功能实体>"]
related: [kb:<module>:frontend:<topic>]
evidence:
  - id: nav:<kind>:<stable-key>
    role: entry                 # entry | rule | implementation | state | data
    confidence: verified        # verified | ast | candidate
---
```

`aliases/questions/entities` 是主语义索引，不再另外复制生成 `business-index.yml`。`evidence` 是声明式绑定；正文中的 `file:line` 会在构建检索索引时补成文件节点绑定。

按业务流组织。每个 `<序号>-<中文业务域名>-flow.md` 固定 3 大块 + 尾部技术证据索引。

| # | 块 | 必填 | 数据源 |
|---|---|---|---|
| §1 | 业务全景 | ✅ | flows + 行为索引 + 用户确认的业务术语 |
| §2 | 字段级页面逻辑 | ✅ | **只从 `field-lineage/pages/*.json` 渲染** |
| §3 | 改动决策卡 | ✅ | reverse-index + timeout/ui/product-limits + file-graph |
| — | 技术证据索引（尾部）| ✅ | navigation JSON + `file:line` |

**禁出现**（§1/§3 正文；§2 允许展示接口原始字段名）：
- 函数名（除非反引号包裹 + 中文括注）
- IPC 通道名 / 事件名（同上）
- 毫秒数 / 字节数（必须翻译为业务语言）
- 文件路径（除非在尾部技术证据索引）
- 英文状态名（必须配中文括注：`pending（等待处理）`）

**业务术语翻译**：所有翻译来自 `manifest.business_terms`；不在表中的术语先进入 Step 2.9 确认，禁止写占位结论。

详细模板见 `references/role-templates.md` § 2。

## Layer 2: `docs/<module>/frontend/`

3 个文件，每篇必须以**一行元数据头**开始：

```markdown
> 提要：<1-2 行>
> 元数据：Summary=<核心要点>；适合读=<角色/场景>；不适合读=<角色>；证据入口=<navigation 文件 + file:line>
```

| # | 文件 | 必填 | 条件触发 |
|---|------|------|---------|
| 01 | `01-架构与调用图.md` | ✅ | — |
| 02 | `02-变更影响导航.md` | ✅ | — |
| 03 | `03-坑点与状态.md` | ✅ | — |

各文件硬性章节要求见 `references/role-templates.md` § 3。

**v3.6 合并关系**：01 合并旧架构/组件/接口图；02 合并变更指南与任务类型差异；03 合并状态时序、失败路径与已知陷阱。

## Layer 3: `docs/<module>/navigation/`

### 设计理念

机器可读的代码图谱 + 行为索引 + 检索路由。AI 工具应能从业务概念、字段、状态、事件、接口、组件、调用链做完整、细致、可追证的检索。

### 文件清单

| 文件 | 来源 | 内容 | 必有/条件 |
|------|------|------|----------|
| `file-graph.json` | nav-parser | 文件节点 + 多类型依赖边 | ✅ |
| `func-dependencies.json` | nav-parser | 导出函数及其调用关系 | ✅ |
| `component-refs.json` | nav-parser | Vue 组件使用、条件、事件 | ✅ |
| `graph-index.json` | nav-parser | 文件级索引（hash/mtime/exports/imports/边） | ✅ |
| `graph-quality.json` | nav-parser | 图质量报告（覆盖率、低置信、unresolved） | ✅ |
| `clusters.json` | graph-cluster | Louvain 聚类、hub、PageRank、betweenness | ✅ |
| `deep-analysis.json` | deep-analyzer | candidate-evidence-only 派生信号（管线/渲染/计算/事件/状态/超时/UI/分支/限制）| ✅ |
| `ipc-flows.md` | Step 2.3 IPC 补证 | IPC 调用链文字描述 | ✅（Electron 项目）|
| `liveness.json` | Step 2.8 验证 | IPC/API 活跃度（active/deprecated/partial） | ✅ |
| `business-index.yml` | 旧版本兼容 | 已由 Markdown 语义元数据 + bindings 替代 | 兼容旧库，不再新生成 |
| **`_intermediate/api-payload-shapes.json`** | data-shape-tracer | payload 形状 + endpoints_by_file 候选 | ✅ |
| `data-shapes.json` | data-shape-tracer `--legacy-copy` | v3.5 兼容副本 | 默认不生成 |
| **`field-lineage/`** | field-lineage | 页面字段溯源、A/B 级权威反向索引 | ✅ |
| **`bindings.jsonl`** | codewiki index | `kb:*` ↔ `nav:*` 多对多绑定 | ✅ |
| **`index.yml`** | Step 4.5 | 无 MCP 时的文本检索后备路由 | ✅ |
| `validation-report.json` | Step 6 自检 | 证据自检（PASS/FAIL + fail 引用列表）| ✅ |

### 候选信号与兼容副本

`deep-analysis.json` 是状态机、UI 反馈、超时恢复、分支和产品限制候选信号的单一来源，检索器直接按 section 建索引。旧库中的 `state-machines.json` / `ui-feedback.json` / `timeout-recovery.json` / `branch-routes.json` / `product-limits.json` 是兼容副本；确认与 `deep-analysis.json` 对应 section 相同后可移除。候选信号必须经 Claude Code 读码补证后才能进入 Layer 1/2 结论。

`_intermediate/api-payload-shapes.json` 由 `data-shape-tracer.mjs` 默认产出；`data-shapes.json` 只有传 `--legacy-copy` 时生成。

### Schema：`bindings.jsonl`

一行一个 JSON，不嵌入 Markdown 正文：

```json
{"knowledge_id":"kb:orders:product:submit","navigation_id":"nav:ui-event:src%2FOrder.vue:click:submitOrder","role":"entry","confidence":"verified","source":"frontmatter"}
```

- `knowledge_id` 必须存在于 Product/Frontend frontmatter，并匹配 `kb:<manifest.module>:<product|frontend>:<topic>`；同模块内唯一。
- `navigation_id` 必须存在于 Navigation 图；不得使用易变数组下标。
- 一个知识条目可绑定多个证据，一个证据也可反向关联多个知识条目。
- `role` 仅允许 `entry/rule/implementation/state/data`，`confidence` 仅允许 `verified/ast/candidate`。
- 正文 `file:line` 投影为带行号的 `nav:code-ref:*` 节点，不得只降级到文件节点。
- `source=frontmatter/code-ref` 属于派生绑定，每次构建重算；删除 Markdown 证据后必须自动清理。无 `source` 或 `source=declared` 才作为人工声明保留。
- Product/Frontend 每篇至少有一个 `verified/ast` 绑定。构建遇到空语义字段、非法枚举或悬空显式 ID 必须失败，不得静默丢弃。

四类信号（`kind`）：
- `external_call_may_fail` — try/catch 包裹的 IPC/HTTP/Bridge 调用

- `runtime_environment_dependency` — 访问 `electronAPI` / `navigator.*` / `process.platform` 等运行环境
- `push_may_be_lost` — emitter/eventBus 订阅且文件内无 reconnect/resubscribe/retry

### Schema：`navigation/index.yml`（无 MCP 后备路由）

格式见 `references/role-templates.md` § 4。固定字段：
- `query_routes`：检索意图 → 主索引 + 兜底索引
- `files`：每个 navigation/ 文件的用途和何时读
- `must_answer`：本模块的 navigation 层必须能回答的问题清单（覆盖度自检）

### Schema：`validation-report.json`（v3.5 扩展）

`--validate` 现在校验三类引用：
- 代码事实引用：`<file>:<line>`，文件必须存在 + 行号有效
- UI 文案引用：`i18n_key + locale_file:<line>`（locale 文件存在 + key 在该文件中可定位）

  "failed_refs": 0,

|---|---|---|
| A | ratio ≥ 0.90 | 健康 |

| D | ratio ≥ 0.30 | 证据严重不足 |
| E | ratio < 0.30 | 不可靠 |

### Schema：`_review.md`（v3.5 新增）

`--validate` 同时生成 `docs/<module>/_review.md` 作为模块级健康报告，**禁止手动编辑**——每次 validate 重写。

7 节固定结构：

1. 整体评分（按 product/frontend/quality 等层分组的平均评分）
2. 按文件细分（每篇 Layer 1/Layer 2 的等级、引用通过/总数、扣分点）
3. 待用户确认 (MUST_CONFIRM) — 来自 `manifest.yml/confirmation_checkpoint`
4. 待业务补充（占位符位置）— 来自 `per_file_confidence[*].issues.placeholders`
5. 未验证调用链 — 来自 `navigation/dynamic-flows.md` ⚠️ 行
6. Coverage Assertions Missing — 来自 `manifest.yml/coverage_assertions[*].status=MISSING`
7. AI 实际检索缺口 — 来自 `.codewiki/eval-log/*/eval-log.yaml` 中 `retrieval_intents` outcome=`not_found`/`partial` 且 `kb_section` 指向本模块的项

第 7 节连接 fe-* skill 的 retrieval_intents 闭环：揭示 AI 真实跑业务时本模块知识库哪些问题被反复问到却找不到。`是否同时静态缺失=❌` 的项尤其重要——文档可能写了内容但 AI 检索找不到，需要重写或加索引。

## 反捏造规则细化（v3.6）

旧的"全产物 file:line"硬约束按事实类型分级：

| 事实类型 | 证据要求 | 缺证据时的处理 |
|---------|---------|--------------|
| 代码事实（链路、字段、状态、超时值） | 必须 `file:line` | 删除或标"未在代码中找到证据" |
| 用户体验事实（文案、弹窗、提示） | UI 触发点 + i18n_key/literal + `file:line` | 标"待文案确认" |
| 业务术语翻译 | 必须来自 `manifest.business_terms` 或会话明确给出 | 写"<原始名>（待业务确认）" |
| 产品限制/不可承诺项 | 必须有 `deep-analysis.json#product_limits` 信号 OR 由外部依赖性质推导 | 标"由实现能力推导" |
| 业务规则 why | 优先代码注释 / commit / 用户输入 | 写"待业务确认" |
| 工作量/影响面 | 必须为可数维度（文件数/IPC 数/状态数）| **严禁输出小时/天/人天/sprint 估算** |

**工时硬约束**：codewiki 严禁在任何产物中输出"小时""天""人天""sprint""工时""周"等估时单位。PRD 影响面评估只输出**可数事实**（触达页面数、接口数、状态数、外部依赖数等），让 PM 自行估时。

## General Rules

1. **所有文档必须中文**，技术术语保留英文
2. **每个语义文档必须先有稳定 ID frontmatter；其后的第一段是 `> 提要：...`**
3. **Frontend 文档必须有 v3.6 一行元数据头**（Summary / 适合读 / 不适合读 / 证据入口）
4. **Product 文档 §1/§3 正文严禁出现技术细节**（函数名/IPC/毫秒/路径/英文状态名），全部下沉到尾部"技术证据索引"；§2 允许接口原始字段名
5. **业务术语翻译只能用 `manifest.business_terms`**
6. **Layer 1 flow 文件命名**：`<序号>-<中文业务域名>-flow.md`
7. **Layer 2 文件命名**：固定为 `01-架构与调用图.md` / `02-变更影响导航.md` / `03-坑点与状态.md`
8. **路径相对项目根**
9. **严禁占位内容**——每条记录来自实际代码或 navigation JSON
10. **YAML/JSON 必须合法**
11. **优先用脚本输出定位结构事实**；动态链路和候选行为信号必须读码补证
12. **Hub 和 critical nodes 获得更深解释 + Mermaid 图**
13. **按权重优先级**：main flow 优先
14. **动态链路必须由 Claude Code 读码补证**；Electron IPC 只是可选 profile
15. **多入口/多模块拆分 target 执行**
16. **目录结构**：`product/`（Layer 1）, `frontend/`（Layer 2）, `navigation/`（Layer 3）
17. **检索入口必须完整**——`bindings.jsonl` 不得有悬空 ID；`codewiki_explore` 是主入口，`navigation/index.yml` 是无 MCP 后备
18. **`coverage_assertions` 必须填全 12 个 topic**——MISSING/PARTIAL 项要给出 reason
19. **严禁工时估算**——PRD 影响面只输出可数维度
